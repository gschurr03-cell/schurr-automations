# Client setup templates

The private `/manage/clients` workspace follows the four current public offers: AI receptionist and lead response; websites and chatbots; local SEO and Google reviews; custom software and workflow automation. It is an owner-only preparation workspace, not a multi-tenant execution service.

Each client has a saved business brief, selected offers, approved public FAQs, separate staff-only knowledge, USD price rules, application field mappings and non-secret connection notes. Updates use revision checks. The ten reusable templates prepare receptionist instructions, inquiry email/owner-alert drafts, website content, approved public answers, fair review requests, review-response drafts, local-profile comparisons, quote calculations, sourced staff answers and mapped application records.

Samples run locally without providers or network actions. The normal, stopped, previously processed and missing-information cases show decisions and prepared output. A duplicate example flag is not a live deduplication store. Drafts do not prove delivery, Google publication, booking or a working connector. The receptionist/website brief templates do not offer an event-level missing-data case because they use the saved business brief; missing profile fields are validated separately. Sample results retain the exact setup revision and become visibly stale after edits. Public and staff knowledge never share a runtime lookup. The owner-only setup export intentionally contains both for implementation review.

The setup download is versioned JSON with business information, workflow requirements, prepared receptionist instructions, sample inputs/results, remaining connections and launch checks. It contains no provider credentials, Schurr runtime defaults or enabled live actions. Profile values and custom sample inputs reject recognized credential patterns; operators must still keep any passwords and secrets out of free-text fields. URLs are not fetched by this workspace.

Production clients need an isolated deployment/database and provider account or subaccount, approved credentials in a secret store, implemented source/destination adapters and client sign-off. The existing Schurr receptionist and first-email infrastructure can be reused as implementation foundations, but it is still configured specifically for Schurr. Saving this setup does not retarget that infrastructure. Booking, transfer, multi-step messaging, live website chat, Google integrations and arbitrary application writes require their respective implementation and connection work.

The public website and `/demo/` now include native `tel:+19857710552` actions and the visible number (985) 771-0552. These start a real phone call through the visitor's calling application, not an embedded browser voice session. The live-call notice explains that an agreed follow-up creates a real request for Gavin. The separate interactive examples remain scripted. Native booking was added in a later release; live transfer remains disconnected. See the native operations section and current readiness audit.

Validation: the client-setup SQLite integration suite covers owner/origin authorization before private reads, duplicate creation, competing revisions, profile validation, ten template outputs, source separation, permission and review eligibility, exact quote arithmetic, field mapping, per-client exports, stale sample protection and delete cascades. CRM render checks cover inaccessible/empty/populated setup pages. TypeScript, existing authentication/intake security and public content checks are part of the release verification. Browser hydration and a new real phone audition are not implied by these checks.

## Native operations and recorded launch checks (October 2, 2026)

The CRM now includes `/manage/schedule`: native phone appointments, weekly availability, per-appointment buffers, minimum notice, booking horizon, blocked commitments, cancellations and downloadable calendar files. Code defaults start disabled. The Schurr runtime now has an approved weekday 8 a.m.–8 p.m. America/Denver booking seed; priority callbacks remain disabled. The owner must verify the displayed availability and block outside commitments. No Google Calendar sync, customer confirmation, background notification or live transfer is implied. Existing outside commitments must be blocked manually.

The receptionist connector installs five custom functions using the existing signed inbound-call endpoint: current calendar rules/availability, confirmed appointment booking, current same-call appointment lookup, confirmed same-call rescheduling/cancellation and a priority callback task. It preserves unrelated remote tools and the existing voice/model. Browser voice calls remain dry runs. Callers must first save a confirmed phone request; mutable CRM numbers cannot silently replace the phone they confirmed. Appointment writes reject conflicts and stale settings atomically. A repeated booking returns its original receipt, including cancellation state. Contact withdrawal stops reminders but does not cancel an appointment; cancellation requires a separate explicit action, available to the same verified call or the owner.

Incoming requests can create a manual personal follow-up reminder, or record a customer reply. The queue stops when the request is handled, paused, booked, replied to, suppressed or its contact changes. No automatic messaging or inbox reply detection is connected. Reminders use the displayed contact and timezone; stale values are rejected. Priority callbacks carry no promised response deadline.

Each client brief has saved evidence for the applicable launch checks, with result, environment, owner and timestamp. A change to the brief invalidates old evidence; a change to another check invalidates prior sign-off. A current test pack and all prerequisite checks are required for scoped approval. Explicitly deferred capabilities, such as email, remain deferred and are not counted as passed. Concurrent changes to the exact approval scope require another review. These records document owner testing; they do not certify that a provider is connected or switch client services on.

Validation includes real SQLite tests for reservation races, buffers and blocks, DST gaps and ambiguous local times, contact/mode changes, replay after cancellation, transactional rollback, stop rules, scoped email deferral, malformed outcomes and approval races. No real customer message or call is part of these tests.


## Isolated installation package

Each saved client brief exports `client-install.json`, `preflight.mjs` and an implementation README bound to the exact saved revision and fingerprint. Fill the target resource references and run `node preflight.mjs client-install.json`. The checker verifies the exact brief fingerprint, selected scope, distinct resource references and disabled live actions. It performs no network calls, provisions nothing and does not establish isolation or access. Replace deployment identity in the listed files, use separate accounts/database, and record real acceptance evidence before enabling each channel. Unknown credential fields and mismatched capabilities fail the checker.

The README groups preparation, connections and controlled acceptance checks by the selected offers. It retains stale/deferred launch states and lists missing fact labels without copying private brief values, inboxes, prices, staff knowledge, mappings, account notes, custom samples or free-text evidence. Download fresh files after editing the brief; a checklist is not a verified provider connection or client approval.

The source is still configured specifically for Schurr. `lib/automation-desk.ts` identity guards, `lib/search-reports.ts` and the desk’s property choices, `lib/site-seo.ts` canonicals/page imports, `lib/booking.ts` calendar identity, and email test/domain wording need client adaptation. Keep validation and owner authorization intact. The manifest does not replace these values, import a brief into runtime settings, deploy infrastructure or implement missing adapters. Live-transfer preparation requires voice preparation; native owner booking, external calendars and SMS are not inherently dependent on voice.

The v53 handoff additions passed three focused groups and the 13-group client-setup suite, with TypeScript checked after integration. No actual client export, isolated client provisioning or live delivery was performed. The production build passed; browser behavior remains unverified.
